
# 設計判断・トラブルシューティング・運用知見

このドキュメントは，設計意図・判断理由・試行錯誤の記録をまとめたものである．


---

## 1. 大まかな方針

* 研究会の複数人で利用可能で複数人でカスタマイズできる運用
  * →完全無料を第一に
  * →ローカル端末での環境構築なしで内容を変更できるようにする
  * →GASなどで通知側のフォーマット修正を容易にする
* 確実に動かし続けなければいけないサービスだというわけでもない（特に通知側が故障してもOK）．
  * →エラーハンドリングをしっかりやらなくてもいい．
* 「新しい論文（文献）を知る（通知してもらう）」のが大事であり，「全てを知らなければない」わけではない．
  * →網羅性が多少落ちても許容（DBをScience of Science的に生かすならそこは記す必要あり．ただ質的分析ならいくつかみるのでも可能なアプローチありだろう）


## 2. 技術選定


- **GAS** 選定理由 -「研究会等のコミュニティでの共同管理・運用調整のしやすさ」を優先したため．
  - **複数人運用のしやすさ**：Google アカウントで共有設定するだけで，複数のメンバーを開発・運用に即座に招待できる．現代では Google アカウントが普及し，研究会でもアカウントを持っていたため，GAS が第一候補として上がった．
  - **編集のしやすさ**：ブラウザ上で収集キーワードの微調整，通知メッセージの文面編集，実行ログの確認が完結する．「このキーワードも拾いたい」「通知メッセージのフォーマットを変えたい」といった調整を容易に行える．ファイルを分離して1プロジェクトにまとめるのも容易であり，メンバーは「収集系」「通知系」の関数にすぐアクセスできる．
    - **【補足】** ただし現状の設計では，Discord の チャンネル・キーワード別通知は DB (Supabase) の特定のテーブルで Webhook の値を設定するやり方になっている．
  - **定期実行のしやすさ**：日次収集（`dailyCollect`）や週次通知（`weeklyNotify`）のような定期実行処理を，標準のトリガー機能のみで運用できる．
- **Groq 選定理由** — カード登録不要（Gemini の課金トラップ回避）．


## 3. 構成・設計判断

### 構成判断

- **Discord bot Worker と LLM評価 Worker を分離した理由** — 関心事・環境変数・デプロイサイクルが完全に独立．統合すると片方の更新がもう片方を巻き込むリスクがある


###  個別アプリケーション・コンポーネント等での判断

- **LLM評価を1論文×1トピック=1呼び出しにした理由** — 複数トピック一括評価ではJSONスキーマを明示しても類似項目等のスキップ・重複が経験的に発生する場合があるため，安全策として1つずつ評価させる設計に
    - **【補足】** 戻ってきたデータの長さチェックやプロンプトの工夫（元のものと紐付けやすいアウトプットも返却させるなど）のような対応が考えられるが，今回は省いた（件数がそこまで多くなくて無料枠で処理できればよいとした）．スケールを大きくするなら，もっと大きなチャンクでの評価＋エラー救済処置組み込みが考えられる．
- **Supabase の API キーを Secret key（旧 service_role）に統一した理由** — Publishable key + RLS無効はSupabaseの想定外の組み合わせでERROR表示が出る．GAS・Worker ともにサーバーサイドなので Secret key が適切 (その上でRLSを有効にした)
- **`summarizeArticle` にオプションオブジェクト `opts` を導入した理由** — `GROQ_API_KEY` のグローバル状態のみに依存する設計では，同一実行内で「この呼び出しでは要約する／しない」を切り替えられない．`useLlm` で呼び出し側が明示的に制御し，`maxChars` で文脈に応じた要約長（検索結果200字・一覧150字・LLM推薦100字）を指定できるようにした．後方互換性のため位置パラメータではなくオプションオブジェクト方式を採用
- **実行タイミングとデータ収集の範囲** `YYYY` でしか取らない `collectJstage` などでは，12/31（の定期実行後）登録の論文などを取れるように，1月実施時には `fromYear` を前の年にするようにしている．`isWithinLastNDays` も実行タイミングのブレを考えて2日にした．
- **`weeklyNotify`** の429エラー対策（Discord側） - 現状力業で `sleep` を各処理の間に挟んでいる．しっかりやるなら，エラーが出た場合の例外処理（上限設定つき繰り返しで再送＋待機など）を組むことができるが，通知側がたまに機能しないぐらいは致命的ではないと判断し，とりあえず力業．
- **J-STAGEの `publication_date` での妥協** - J-STAGEで使ったAPIでは，`pubyear` で出版年は取得できるものの，月・日は入っていないかもしれない（レスポンスフォーマットに見当たらなかった）．個別の書誌情報では獲得できるが，今回は，工数等を考え，代用として `updated` を用いることとした．実際の出版日と異なることに注意．

### データベースに関する判断

- **`paper_key` と `doi` の分離理由** — DOI を持たない論文（紀要・プレプリント）への対応．元は `doi` を UNIQUE キーにしていたが，md5 ハッシュのフォールバックを含む `paper_key` に変更した経緯
- **`collection_sources` を TEXT[] 配列にした理由** — 同じ論文が複数ソースから来る場合に上書きではなく追加する設計．元は TEXT 単体だった
- **`updated_at` を DB に持つがユーザー機能には露出させない判断** — 「今週更新された」は実用価値が低いが，運用デバッグには有用
- **`works_topics` ジャンクションテーブルの採用理由** — Push 型通知時に毎回全文検索するのは無駄．収集時に紐づけておけば JOIN 一発
- **`subscriptions` テーブルを `topics` から分離した理由** — topics はグローバルなキーワード一覧．「どのサーバーのどのチャンネルにどのトピックを送るか」は別の関心事．複数サーバーで使えるようにするため
- **`llm_subscriptions` テーブルを `subscriptions` と別テーブルにした理由** — `subscriptions` は keyword 部分一致ベースの通知，`llm_subscriptions` は LLM スコアベースの通知であり，データソースとフィルタ条件が異なる．`subscriptions` に `type` カラムを追加して統合する案もあるが，既存の複合主キー `(webhook_url, topic_keyword)` の変更が必要になり，マイグレーションコストに見合わない．また `llm_subscriptions` には `min_score`（チャンネルごとの閾値）という固有カラムがあり，NULL 許容で統合するより別テーブルの方が制約が明確になる．送信ロジックの重複は `sendTopicDigest` 共通関数への切り出しで対処した．

## 4. トラブルシューティング記録

- **Discord の Interactions Endpoint URL と Webhooks Endpoint URL** — インタラクティブな bot の構築では Interactions Endpoint URL を使う．うっかり後者を指定した（後者では PING 検証が行われず，適当な URL でも保存できてしまう可能性？）
- **GAS の「新しいデプロイ」vs「デプロイを管理」** — 前者だと URL が毎回変わり Workers の環境変数を更新し続ける羽目になる．後者で既存デプロイを編集すれば URL 固定
- **`getWeeklyHits` の引数形式** — オブジェクト `{ topic, mode }` ではなく2引数 `(topicKeyword, mode)`．間違えると `results.forEach is not a function` エラー
- **`getWeeklyHits(null, "added")` は「全トピック一括」ではなく「トピック未登録」エラー** — トピックごとにループで呼ぶ必要がある
- **Zenodo 論文の混入** — OpenAlex keyword 検索で Zenodo 由来のデータセット・ソフトウェアが大量に混入（141件）．DB からは `doi LIKE '10.5281/zenodo.%'` で削除済み．再発防止は OpenAlex のクエリに `type:article` フィルタを追加することで対応済み
- **CloudFlare の Dashboard での Worker 作成時の「build process」エラー** — Upload ではなくインラインエディタを使えば回避できる
- **Error 1031 (Invalid Workers Preview configuration)** — `compatibility_date` と `nodejs_compat` の設定が必要（Ed25519 に必要）
- **Discord 2000文字制限** — 全トピックまとめて送ると超過する．トピックあたりの文字数を按分するか分割送信で対応
- **OpenAlex API の `|` エンコーディング** — GAS の OpenAlex 関連の処理（`fetchOpenAlexPages`）では， URL 中の `|`（パイプ）がそのままでは正しく処理されない場合がある．OpenAlexに関しては，`%7C` にエンコードして渡す．ブラウザでは `|` のまま動作するため気づきにくい可能性あり．
- **LingBuzz の An invalid XML character エラー** — サニタイズ処理を追加（単純置換での副作用は未検証）．
- **PGroongaでの使用容量肥大**- 全文検索に関して PGroonga の利用を考えて拡張をonにしたが，数日の試行で Supabase が500MB制限の60%に到達．ここで PGroonga を DROP した．ただし肥大した容量は残る模様？　（全文検索は ILIKE で行い，トピックとのマッチングは Groq を通して行う方針．）
  - **PGroonga を DROP した理由の詳細** — 日本語全文検索を検討した．手段として `pg_bigm`（2-gram インデックス）を探したが，Supabase の利用可能な拡張一覧に見当たらず，代替として PGroonga を採用した経緯がある．これは高速な検索を行える拡張機能である．しかし運用の結果，以下の 点から DROP した．(1) 【容量の問題】Groonga の独自ストレージが初期オーバーヘッドだけで約 280 MB を消費していると推定された（Supabase フリープラン 500 MB のうち 300 MB 近くが使用されていたが，実テーブル・インデックスの合計は約 6 MB に過ぎなかった）．`pg_bigm` が Supabase で利用可能になった場合は再検討の余地あり．(2) 【現状の構成】現時点で `searchWorks` も `matchWorksToTopics` も実際には PGroonga を使わず `ILIKE` と `indexOf` で完結している．(3) 【検索方法のメリットがどれだけあるか】(P)Groonga では形態素解析に基づく検索が行えるが，言語学の専門用語に対してはその効果が高くないかもしれない（特にチューニングなしでは，不適当な分割となる可能性もある）．また，検索は名詞（トピック名等）が中心だと予想され，動詞・形容詞等の活用を吸収するメリットがあまりないのではないか．また，このプロジェクトの特徴からすると，意味的なマッチングのほうが重要かもしれない．トピックの表記バリエーションへの対応や，（明示されない）「分野」等に該当するかを判定することを考慮し，LLM判定が考えられる．（本プロジェクトでは通知と別のタイミングで関連度データが構築できることから）LLMでの意味的な関連度判定を行うほうが効果があるのではないか． (4) 【高速性が重要かどうか】このプロジェクトの主要件は週次通知であり，インタラクティブな bot の `searchWorks` は副次的機能である．将来レコード数の増加で `ILIKE` がタイムアウトするようになった場合，bot 側の検索を切り捨てる選択肢がある．`works_topics` の紐づけは `matchWorksToTopics` で新規追加分のみ処理する構成のため，全件スキャンの負荷は通知側には波及しない．
  - **構成についての補足**：意味的な揺れの吸収は LLM 評価層が担っており，形態素解析レベルの改善は不要．英語側の `fts_en`（tsvector, 約 2 MB）は将来 `ILIKE` → `@@` に切り替える余地を残すため保持．
  - **容量についての補足**：なお，`DROP EXTENSION pgroonga` を実行しても，Groonga の外部ファイルは PostgreSQL の管理外にあるため，ディスクから解放されないらしい（ https://note.com/miseriku/n/ndc34310e58e7 ）．Supabase では superuser 権限がなく `pgroonga_vacuum()` も空振りするらしい．残容量に余裕がある間は放置し，逼迫した時点で DB 再作成（新プロジェクト作成 → スキーマ＋データ移行 → 接続先切り替え）で対処する．
- **CloudFlare 無料版の制限の対策** — LLM の eval (llm_eval) で対象 topic 数と対象 paper 数を増やすと `Too many subrequests by single Worker invocation. ` のエラーが観測された．今は環境変数 `LLM_EVAL_MAX_PAPERS` の調整（と cron の頻度←目的：未評価 works が積み増されないため）でエラーを抑制する方針にしているが，評価対象のtopicsを増やしていくなら根本的に処理を工夫することを検討（分散実行、Groqリクエストをまとめる）．


## 5. 運用上の知見

- **トピックマッチングの限界** — 分野名（「社会言語科学」等）等の， title, abstract に直接記入することが多くないであろうものの検索をどうするか．指定トピックでの検索（分野なら分野指定検索）ができないようなデータソースにおいてこのようなものを探す場合には，(1) 分野ならば関連性が強いジャーナルを指定して検索する， (2) そのトピックとの関連性が強いキーワードを指定して検索する，(3) 広めにデータを取ってからの LLM を用いたマッチングを行う，等が検討できる．
- **`CMC` と `computer-mediated communication` の重複** — 同概念だが両方残存させて様子を見る．CMC はノイズが多いが，`topics` テーブルからは削除していない．
- **publication_date の未来日** ――ジャーナルのadvance publicationにより，`publication_date` が実際の取得日より先の日付になることがある．下限フィルタ（>=）のみであれば影響しないが，上限を `CURRENT_DATE` で切るクエリを書く場合は未来日の論文が脱落する点に注意．
- **Cloudflare Workers の `ctx.waitUntil()` で長時間処理は不可** — HTTPトリガーのバックグラウンド処理は数十秒〜数分で強制キルされる．Groq の TPM 制限回避の sleep を挟む処理には Cron Trigger（15分保証）が必要
- **Cloudflare Workers で `fetch` ハンドラなしはデプロイエラー** — Cron 専用 Worker でも空の `fetch` ハンドラ（`return new Response("Not found", {status: 404})`）が必要
- **OpenAlex のページネーション（cursor）がコメントアウト状態** 現状 1ページ（100〜200件← `per_page` 指定）のみ取得
  - 経緯: 開発時は，デバッグや初期データ投入期の大量取得によるDB容量の肥大化・GAS6分制限を等を懸念して1ページ固定
  - トライアル時：1度に100件以上入ることもあまりなさそうなのでこのまま運用
  - 今後の対応: 2ページ以降ある場合の漏れに対応しては，`MAX_PAGES = 3` などの安全装置（上限ガード）を付けた上でループを有効化するのが望ましいか？　（とはいえ `MAX_PAGES` の値は要検討である←上限を設けると網羅性保証にかんして考える必要が出ると考えれば，ループの有用性がどの程度あるか？）


## 6. 将来の移行・変更可能性

- DB 容量・権限制約からの解放のための移行を検討する可能性はあり．
  - 個人用なら別の環境に移行するメリットもさらに考えられる．
- 何かの役に立つか（用途例；プロンプト改良）と，`llm_topic_relevance` テーブルの `reason` にLLMの判断コメントを入れているが，容量削減のために削ってもいいか（特にかなりの低スコアなら）．
- LLM 評価対象の topics を増やしていくなら，根本的に `llm-eval` まわりの処理を改修することを検討（`Too many subrequests by single Worker invocation.` 対策）．
